# 后续版本交付约定

用户于 2026-10-17 明确要求：准备部署到 GitHub，因此后续更新必须提供完整 GitHub 文件。

用户随后反馈 HTML 入口不明显。后续优先提供“GitHub网页托管版”：ZIP 最外层直接包含完整自包含 index.html，使用 GitHub Pages 的 Deploy from a branch / (root) 发布；完整模块化源码保留在 source/ 内。继续提供完整包，不只给补丁。使用 make-github-web-package.py 在完整源码包生成后产出该网页包；两种部署说明必须区分，避免用户同时启用两种工作流。

每次更新继续维护同一个游戏项目，并交付完整可上传的 GitHub ZIP，包括全部网站文件、独立机制和图形、部署配置、校验脚本、离线版、版本说明和必要教学文档。不要只交付改动文件、补丁或临时预览网址。

保留同一站点路径、存储键及已发布题目 ID，新增题目使用新 ID。说明当前已实现与尚未实现的范围。版本变化后同步 package.json、CHANGELOG.md 与 GitHub README，运行内容检查并重新生成离线版和完整包。打包使用 make-github-package.py 的明确白名单，排除原始 PDF、Sites 内部元数据、Git 历史、令牌和个人备份。

未经用户进一步指示，不替用户创建 GitHub 仓库、提交文件、改变仓库权限或设置域名；完整文件包先作为可 review 的交付物提供。用户自己部署时，说明 GitHub Actions 的设置与网址迁移后的进度导入方法。
